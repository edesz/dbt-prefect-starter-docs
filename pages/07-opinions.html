Opinions

Project Organization

In order to follow dbt’s best practices for project structure, the project organization starts with the defaults provided during project initialisation using dbt init.

After initialising a new dbt project, the models/example directory is removed, but otherwise the default structure is kept unchanged. The intention is to provide enough structure to make the project immediately usable without imposing a particular modeling methodology.

While different projects may organize their models in different ways, a staging layer is a common starting point for transforming source data into a consistent form. For this reason, the template includes a small staging model example in the models/staging directory.

The example staging model is organized in its own subdirectory. The associated sources.yml, schema.yml, and SQL files follow a consistent naming convention that makes their purpose and relationship to the model clear. For example, for a model named <model-name> located under models/staging/<model-name>, the source definition and model files would follow the pattern _stg_<model-name>__sources.yml and _stg_<model-name>__records.sql respectively in order to follow dbt’s best practices. The leading underscore also keeps these supporting files visually distinct from the model itself.

Standalone repository

A dbt project can be organized as either a standalone repository or as part of a dbt monorepo. A standalone repository contains a single independent dbt project, while a monorepo can contain multiple dbt projects alongside other related code and resources.

This template uses a standalone repository design. Since its purpose is to provide a starting point for an individual dbt project, keeping the dbt project in its own Git repository keeps the scope and project boundaries clear.

A monorepo may be appropriate when multiple dbt projects need to be managed together, but that additional organizational structure is outside the scope of this starter project.

Python Virtual Environments at the Root of Everything

Reproducibility starts with the computational environment in which the project runs. This project aims to have every part of the workflow - including just running individual dbt commands - to execute within a defined Python environment whose dependencies could be recreated reliably. Python package management was therefore treated as a foundational part of this starter project rather than something left to an individual developer to configure.

The goal is simple that a new user should be able to recreate the environment used to develop and run the project without having to determine which packages, versions, or dbt adapters were installed.

For Python dependency management, this project uses Pixi by default, with the combination of tox and uv provided as an alternative. Both approaches allow the project’s dependencies and environment configuration to be captured in files that can be committed to version control. With Pixi, this configuration is specified in pyproject.toml. For tox and uv, it is defined through tox.ini. This makes the environment part of the project itself rather than a collection of undocumented local setup steps for the user to execute one at a time.

The same principle applies when running dbt commands outside of an orchestrated workflow. For example, an ad hoc command such as dbt deps should execute in the project’s defined environment, where dbt-core and the required database adapter, such as dbt-duckdb, are already installed. This keeps interactive development, automated workflows, and orchestrated pipelines aligned in terms of their dependency definitions and it reduces the risk of a command working on one machine but failing on another.

Ad-Hoc dbt Commands

Running ad-hoc dbt commands quickly is essential for maintaining momentum and accuracy during data development. When building or debugging data pipelines, users frequently need to test small changes, inspect intermediate models, or run specific tests without waiting for the entire project to compile and execute. Prompt execution of commands like dbt run --select my_model or dbt test provides immediate feedback, allowing you to catch syntax errors, logic flaws, or data quality issues in real time.

This rapid iteration cycle minimizes context switching, reduces development friction, and ensures that you can prototype data models fast. It lowers the barrier to entry and supports following best practices from the beginning. This template supports running fast ad-hoc dbt commands out of the box.

In this project, an adhoc dbt command runs in an environment pre-configured using Pixi. So, the user does not have to waste time wrestling with missing dependencies or sluggish execution environments just to run a single model.

Ultimately, supporting ad-hoc dbt commands prevents this starter project from becoming a bottleneck as the project grows.

DAG for End-to-End dbt Pipelines

A dbt project is more than a collection of individual commands. In practice, a complete workflow often consists of multiple dbt operations that need to be executed in a particular order. The dbt CLI executes one command at a time, so commands that are part of a larger workflow must be composed using a shell script, task runner, orchestration tool, or some other mechanism. For example, a workflow may require dependencies to be installed before building models, or may need to generate documentation after the project has been built.

The important distinction is between running a sequence of commands and defining a workflow that manages that sequence. A simple shell command such as

dbt deps && dbt build

can execute two commands in succession. However, as a workflow becomes more complex, it becomes useful to explicitly define the dependencies between its steps and provide a mechanism for executing, monitoring, and retrying those steps.

Scenarios for Sequential Execution of Commands

There are several situations where a dbt workflow may involve multiple distinct commands. Below are some examples.

Checking source freshness before a build

Source freshness can be evaluated separately from the build when freshness is an explicit prerequisite for downstream processing

Unlike a simple sequence of dbt commands, a workflow here can use the result of the freshness check to determine whether the subsequent build should proceed at all.

Generating documentation

Documentation generation is another distinct dbt operation that may be part of a larger workflow

The build establishes the current state of the project and its database objects, after which dbt docs generate can produce the artifacts used to serve the dbt documentation site.

Managing snapshots and downstream models

Snapshots may also be treated as a distinct stage when a workflow needs to capture changes in source data before building downstream models

The important point in each of these examples is not that dbt cannot execute the individual operations. It is that a complete data workflow may contain several operations whose order and success criteria need to be managed together.

Why Use an Orchestration Tool?

Running sequential dbt commands from a terminal or shell script is useful for simple workflows, but it leaves the workflow logic largely in the hands of the user or script executing it. As the workflow grows, additional concerns may emerge

  1. task dependencies
  2. retries
  3. scheduling
  4. logging
  5. visibility into failures

Two important properties of a data modeling workflow are correctness and reproducibility. A model should not only produce the expected results, but should also be possible to rerun using the project’s source files and dependencies without relying on undocumented steps or a particular developer’s local environment. Testing is central to establishing correctness, while explicitly defining the modeling workflow as a directed acyclic graph (DAG) makes the dependencies between transformations clear and provides a reproducible execution path.

This is where orchestration becomes important. Ad-hoc dbt commands remain useful for development, but the complete workflow has a repeatable path that can be executed reliably whenever needed.

Data orchestration is the process of scheduling, running, and monitoring open-source dbt Core jobs in production. Unlike dbt Cloud, which includes a built-in scheduler to do this, dbt Core is a command-line tool. That means we need an external orchestrator to handle dependencies, run triggers, retry failed tasks, and alert your team when things break

An orchestration tool provides a layer around the individual dbt operations. Instead of thinking of the workflow as a list of dbt commands to execute, each operation becomes a task with defined dependencies and execution state. This makes the workflow easier to automate, observe, and re-run.

This distinction is important for this starter project.

Important

The purpose of adding an orchestrator is not to replace dbt’s own capabilities or to make a small local project unnecessarily complex. It is to capture how dbt commands can participate in a broader orchestrated workflow while keeping those commands themselves unchanged.

Prefect as the Orchestration Layer

There are many tools for orchestrating workflows and representing DAGs, including Airflow, Luigi, Snakemake, Prefect, and Dagster. This project uses Prefect together with its dbt integration because it provides a Python-native way to define and execute workflows while keeping the dbt project itself independent of the orchestration layer.

In this template, individual dbt operations are represented as Prefect tasks within a Prefect flow. The relationship between Prefect tasks is explicitly defined, and Prefect manages their execution state.

The resulting workflow is more than a sequence of terminal commands. Prefect provides a defined workflow for executing dbt commands and their dependencies, while also making that workflow available through simple project entry points. The result is a pipeline that can be run interactively during development or from a clean state when reproducibility needs to be verified.

ImportantPrefect Cloud Benefits for dbt

Here, we are using Prefect Cloud’s Free Tier which offers some key benefits for a dbt project

  1. No infrastructure to maintain
    • Prefect handles the scheduling, user interface, and cloud-hosted control plane, which eliminates the need for you to self-host Prefect Server or configure dedicated worker infrastructure for light workloads.
  2. Free serverless compute
    • The Free Tier includes free monthly serverless execution minutes (typically 500 minutes) to run your dbt flows directly in Prefect’s cloud environment. Prefect’s hybrid architecture means that you get the following privacy benefits
      • Your workflows, code, and data stay inside your own private network or cloud account.
      • The workers in your network poll the Prefect Cloud API for instructions using outbound-only requests. This means Prefect Cloud never opens inbound connections into your network.
      • Prefect Cloud will only handle the control plane, coordination, and scheduling of your workflows. Your actual data processing never flows through Prefect Cloud servers. Only basic run history, task names, run states, and scheduling information are stored on Prefect Cloud.
      • If you use Prefect blocks to store credentials, those sensitive values are encrypted at rest using cloud key management services.
  3. Remote observability
    • You instantly gain a real-time remote dashboard to inspect your workflow run histories, view structured logs, and catch failed dbt tasks or model runs.

As an example, in a simple workflow, a dbt build must complete before a subsequent dbt docs generate operation runs, as shown below

A shell script can express the same dependency with sequential dbt commands. Prefect adds additional workflow capabilities around that dependency

  1. Task dependencies
    • With dbt, a user can handle this sequence through shell commands or a CI/CD workflow pipeline, rather than inside dbt’s native configuration files. However, a Prefect workflow can explicitly define that a downstream task (docs generate) depends on the successful completion of an upstream task (build). If the upstream task fails, then the dependent task does not proceed as though the prerequisite had succeeded.
  2. Visibility
    • Prefect provides a graphical user intergace for inspecting workflow runs, task states, execution times, and logs. This makes it easier for a user to determine which step failed without having to reconstruct the execution history from the terminal output. dbt’s native visibility dashboards, timing charts, and job monitoring tools belong exclusively to dbt Cloud and not to dbt core that we are using in this project.
  3. Scheduling and automation
    • A Prefect flow can be scheduled to run automatically or triggered by external events. This allows the same workflow used during development to become the basis for an automated pipeline when that becomes useful. The dbt scheduler is not available for dbt core which is used here.
  4. Retries and handling failures
    • Individual tasks can be configured with retry behavior. For example, a transient database connection failure does not necessarily need to cause the entire workflow to be considered permanently failed. Prefect can retry the affected task according to its configuration. You can move beyond basic time-based cron scheduling by using event-driven triggers, retries, and custom logic to kick off your dbt jobs. Here, the retries are set to zero by default, but can be easily changed in the Python source code.

The result is a useful separation of responsibilities. dbt defines the data transformation logic, while Prefect manages the execution of that workflow.

The dbt project remains a normal dbt project, but its commands can also participate in a larger, observable, repeatable DAG when the project needs one.

NoteTesting Prefect Tasks and Flows

Motivation

Unit testing Prefect flows and tasks is critical because it isolates your data engineering logic from network fluctuations, external databases, and live infrastructure dependencies.

By forcing code to execute against an ephemeral, in-memory API, we can validate that task interactions, error-handling retries, and data type schemas behave exactly as designed before deploying code to production. This practice catches logical errors or configuration drifts early in a CI/CD pipeline, drastically reducing debugging times, preventing corrupted datasets, and saving on costly orchestration compute fees.

Implementation Overview

In order to test Prefect 3.x flows and tasks effectively with pytest, the best practice is to isolate the orchestration logic by running against an ephemeral, in-memory API and database.

Pytest has become the industry-standard Python testing framework because it replaces boilerplate code with simple, native assert statements and offers a flexible, modular fixture system that scales effortlessly from tiny scripts to massive codebases. A conftest.py file serves as a centralized configuration hub for a directory, allowing you to define reusable fixtures, plugins, and hooks that are automatically recognized by pytest without needing explicit imports in your test files. Using conftest.py drastically cleans up a test suite by keeping structural setup code, like spinning up an ephemeral Prefect test harness, mocking global database connections, or loading environment variables. This entirely separated from the actual test logic.

In Prefect tests, using a conftest.py file allows for defining a session-scoped fixture that sets up an isolated testing environment once for the entire test suite. This prevents tests from slowing down or writing data to a production Prefect instance.

In this template, a conftest.py was created in the root of the src/tests/ directory. The prefect_test_harness utility was used to spin up the mock backend. Setting scope="session" and autouse=True ensures the harness runs once for all tests, saving significant execution time.

# tests/conftest.py

import pytest
from prefect.testing.utilities import prefect_test_harness


@pytest.fixture(autouse=True, scope="session")def prefect_api_harness():
    """
    Spins up an isolated, ephemeral Prefect API and database 
    once for the entire test session.
    """
    # Increase the startup timeout if your CI environment is slow
    with prefect_test_harness(server_startup_timeout=60):
        yield

Because the fixture in conftest.py is configured with autouse=True, every test in the suite automatically executes within the isolated test harness. We do not need to import or explicitly pass the fixture into the test functions.

With this setup, tests were written in two Python scripts following the naming convention test_*.py and placed in src/tests

  1. test_prefect_tasks.py tests Pefect tasks
  2. test_prefect_flows.py tests the Pefect flow

In order to avoid confusion with the dbt tests folder, Prefect tests were placed alongside the Prefect module code. This is one of the popular test layouts in the Python ecosystem.

Choosing Make as the Project’s Task Runner

make was chosen as the project’s task runner because it is widely available across operating systems and is commonly pre-installed on Unix-based systems. It provides a simple and familiar interface for defining named entry points that execute one or more shell commands.

One benefit of using make as a thin layer over this project’s workflows is that the entry points can remain the same even as the underlying dbt project changes. For example, model directories can be added, removed, or reorganized and dbt_project.yml can change over time without necessarily requiring changes to be made to the Makefile. Similarly, the Python environment used to execute the commands is managed separately using Pixi in pyproject.toml. Make just calls Pixi tasks defined in this file without knowing of any changes that might be made to it.

This keeps the interface for common project operations simple while allowing the user to change implementation underneath it as required.

NoteAnatomy of Makefile Rules Used here

A make rule is a definition in the Makefile that associates a target with the commands that should be executed when that target is invoked. As an example

abc:
    @echo "+ $@"
    @echo "some text"
.PHONY: abc

This rule has three main components

  1. Target (abc)
    • this is the name used to invoke the rule and, in this example, the name abc represents an action to be performed
  2. Prerequisites (none)
    • no prerequisites are listed after the colon here, so the rule does not depend on any files or other targets
  3. Recipe (the @echo lines)
    • these are the shell commands that are executed when the target is invoked

The .PHONY declaration indicates that abc is a command-like target rather than a file that make should consider up to date.

This is useful for task-runner-style Makefiles, where targets represent actions such as running tests, building documentation, or executing a dbt workflow using Prefect.

Tip

Since we are explicitly using make as a task runner here rather than as a traditional compilation/build tool, this walkthrough helps a reader understand why the provided Makefile may look slightly different from the classic make examples found elsewhere.

In this project, each of the two dbt workflows discussed earlier have a corresponding make rule

  1. for running an individual dbt command
  2. for orchestrating a complete dbt workflow with Prefect

Each rule executes within its defined Python environment, so the user does not need to remember the underlying environment activation or command sequence.

Running a workflow is as simple as

make <RULE-NAME>

In this way, the Makefile acts as a small, stable interface to the project’s development workflows. It is not intended to replace dbt or Prefect. Instead, it provides convenient entry points for invoking their commands reproducibly.
